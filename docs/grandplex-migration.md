# GrandPlex migration

## Canonical brand

**GrandPlex** — one spelling, one capitalisation. Not `Grandplex`, `Grand Plex`
or `GRANDPLEX`. Declared once in [`src/config/brand.ts`](../src/config/brand.ts)
and enforced by `npm run check:brand`.

The wordmark stays Latin in both interface languages. A logo is artwork, not a
translatable string. Inside running Bangla prose the transliteration
**গ্র্যান্ডপ্লেক্স** is used, because a Latin wordmark mid-sentence reads as a
foreign object; `brand.banglaName` holds it.

## Booking references

New references are issued as `GP-` + six characters, e.g. `GP-A7K3M9`. Only the
prefix changed — the code after it is generated by exactly the same
deterministic hash as before.

**Existing `NK-` references are not rewritten.** They are printed on tickets
people already hold, saved in calendar entries, and read down the phone. The
reference is the only thing tying a customer to their booking, so changing one
would break the very thing it exists for.

What that means in practice:

| Behaviour | Result |
| --- | --- |
| New bookings | `GP-` |
| Opening an existing `NK-` booking | Works |
| `NK-` in booking history | Displayed unchanged |
| Max recognising a spoken reference | Both prefixes |
| Duplicate protection | Unaffected — it matches on screening, seats and email |
| Confirmation refresh | Unaffected |

One place knows about the legacy prefix: `LEGACY_REFERENCE_PREFIXES` in
`src/config/brand.ts`. `isBookingReference()` and `isLegacyReference()` in
`src/store/bookings.ts` are the only readers. `check:brand` fails if anything
starts *generating* `NK-` again, while leaving recognition alone.

## localStorage keys

**Kept as `nokshi.*`.** Six keys: `nokshi.preferences.v1`, `nokshi.booking.v1`,
`nokshi.bookings.v1`, `nokshi.max.v1`, `nokshi.reports.v1`, `nokshi.watches.v1`.

This is deliberate. A storage key is invisible to customers; renaming one buys
nothing and risks everything. The migration would have to read the old key,
write the new one, and delete the old — atomically, across six stores, in a
browser that can be closed mid-write. The failure mode is a customer losing
their entire booking history to a cosmetic rename.

`check:brand` strips these keys from the source before scanning, so the
exemption belongs to the *string* rather than to whichever file happens to use
it — a new file using the key needs no new allowlist entry, and a new file
using the old brand in prose still fails.

If they are ever renamed, it should be a versioned migration with a fallback
read of the old key retained for at least one release, not a find-and-replace.

## What was preserved

- Every completed booking in local storage
- In-progress bookings
- Max's conversation history
- Saved watches and lost-property drafts
- Cinema, accessibility, language and theme preferences

Nothing in this migration writes to storage on upgrade. The first time a
rebranded build runs, it reads exactly what the previous build wrote.

## Venue names

Five venues were renamed in the catalogue — `Nokshi Dhanmondi` → `GrandPlex
Dhanmondi`, and so on. These are sample data, not customer data. A booking
snapshots its `cinemaName` at the time it was made, so a ticket issued before
the rebrand still prints the venue name it was sold under, which is correct.

## One thing the sweep got wrong

An automated replacement turned `nokshi kantha` — the running-stitch embroidery
of Bengal, referenced in the design system and the About page as the origin of
the sprocket motif — into `grandplex kantha`, which is meaningless. It was
restored to **nakshi kantha**. Worth recording because it is the characteristic
failure of a brand sweep: the old brand name was itself borrowed from a real
word, and a blind replacement damages the thing it was borrowed from.
